# Finora — архитектура v1.0

Продуктовые требования, UX-решения и бизнес-правила определены в `PROJECT.md` и `DISCOVERY.md`. `ARCHITECTURE.md` описывает техническую реализацию этих требований.

Статус: целевая архитектура v1.0 с техническими уточнениями Stage 1. Реализован минимальный Foundation; его фактические проверки описаны в REPORT. Предметные функции, БД, Docker и OpenAPI runtime ниже остаются планом. Порядок работ и критерии переходов находятся в [ROADMAP.md](ROADMAP.md).

## 1. Назначение и источники истины

[PROJECT.md](PROJECT.md) содержит обязательные требования задания, включая все функции варианта 1, минимальный seed, живой Swagger UI, тесты, CI, документацию, историю Git и запуск одной командой. [DISCOVERY.md](DISCOVERY.md) — утвержденная спецификация Finora: продукт, предметная область, UX, ограничения и приемка. Этот документ определяет механизмы реализации, не заменяя эти источники.

Приоритет: `PROJECT.md` → `DISCOVERY.md` → `ARCHITECTURE.md` → `ROADMAP.md` → код как свидетельство фактического состояния. Противоречие источников необходимо явно описать вместе с влиянием и безопасным решением; затронутую работу приостановить, исходные документы самостоятельно не переписывать.

## 2. Архитектурные цели

- Качество для портфолио: законченные пользовательские сценарии, выразительный финансовый интерфейс, понятные ошибки и демонстрируемая надежность.
- Практики промышленной разработки: авторизация на сервере, точная финансовая арифметика, атомарность изменений, наблюдаемость, воспроизводимые проверки.
- Соразмерность проекту: один backend, одна БД, понятные модули без корпоративной инфраструктуры «на вырост».
- Строгий TypeScript, небольшие интерфейсы модулей, повторное использование контрактов и компонентов, удобство сопровождения.
- Проверяемость бизнес-правил независимо от UI, интеграционные проверки с настоящей PostgreSQL.
- Запуск в чистом окружении через `docker compose up` без ручной подготовки; этот критерий блокирует сдачу.

## 4. Общая схема и топология

```text
Браузер
  ↓
Frontend (React)
  ↓ REST /api/v1
Backend (NestJS)
  ↓ Prisma / параметризованный SQL
PostgreSQL
```

```text
Браузер → web (Nginx: статика frontend)
              ├ /api/v1, /docs → api (NestJS) → postgres
              └ остальные UI routes → frontend
```

Compose содержит ровно три сервиса: `web`, `api`, `postgres`. У браузера один origin для UI, API и Swagger; Nginx проксирует API без потери префикса. База доступна backend по внутренней сети Compose, браузер не получает доступ к ней. Публичные порты будут выбраны и проверены в Stage 2; этот документ не утверждает существующий адрес приложения.

Для локальной разработки Vite proxy сохраняет те же относительные `/api/v1` и `/docs`. Это уменьшает различия cookie-поведения между разработкой и Compose. Проверки здоровья backend доступны контейнерным healthcheck по `/health/live` и `/health/ready`.

## 6. Frontend

React Router реализует публичные `/login`, `/register` и защищенные маршруты из `DISCOVERY.md`, раздел 10: `/`, `/transactions`, `/transactions/import`, `/budgets`, `/recurring`, `/categories`, `/audit-log`, `/settings`. Профиль входит в `/settings`. Создание и редактирование операций открываются в sheet/dialog, без отдельного route.

`app` собирает провайдеры, маршрутизацию и оболочку; `pages` компонуют экран; `features` содержат конкретные действия и формы; `entities` — доменное представление; `shared` — независимые примитивы и инфраструктуру. Общий компонент не импортирует страницу или предметную функцию. Не требуются дополнительные слои и каталоги для каждого маленького компонента.

TanStack Query хранит серверное состояние. Ключи запросов включают ресурс, месяц, фильтры, сортировку и пагинацию. После изменения операции инвалидируются соответствующие списки, dashboard, budgets и audit; правило обновляет также блок ближайших операций. Денежные результаты показываются после подтверждения сервера. При logout или смене пользователя весь пользовательский кэш очищается.

Фильтры и страница списка сохраняются в URL; смена фильтра сбрасывает страницу. Поиск имеет debounce. Состояние открытого диалога и шагов CSV-мастера локально компоненту/функции. Глобальный Redux/Zustand store не нужен. Auth provider получает пользователя через `/auth/me`; его наличие в UI не заменяет серверную проверку.

Формы: React Hook Form + Zod для ранних сообщений; API-ошибки полей сопоставляются с формой. Денежный ввод сохраняет десятичную строку, локализованное представление преобразуется в однозначный API-формат. API-адаптер использует генерируемый клиент, cookie и единый обработчик Problem Details; не копирует контракты вручную.

Дизайн строится на CSS tokens и Tailwind: светлая тема, глубокий Indigo, семантические цвета, шаг отступов 4/8 px, умеренные скругления. shadcn/ui и Radix дают основу доступных примитивов. Предметные `CurrencyInput`, `CategoryPicker`, `MonthPicker`, `BudgetProgress`, `AuditDiff` дополняют их по мере потребности. Recharts используется для диаграмм, Lucide — для иконок, Motion — для функциональных переходов 150–250 ms с `prefers-reduced-motion`. Темная тема остается необязательной.

Адаптивность предусматривает sidebar на desktop, нижнюю навигацию `Обзор / Транзакции / Бюджеты / Ещё` на mobile, карточки вместо таблицы транзакций, отдельный filter sheet и подходящий экрану диалог редактирования. Данные и правила общие для обеих форм представления.

Практический ориентир — WCAG 2.2 AA: semantic HTML, labels, клавиатура, видимый focus, focus trap/возврат focus, Escape, контраст и удобные touch targets. Цвет дублируется текстом/иконкой; графики имеют текстовое резюме. Каждый сценарий получает loading, empty, filtered empty, error/retry, success и подтверждение разрушительного действия. Все пользовательские тексты русские, форматирование `ru-RU`.

## 7. Backend

NestJS реализует поток `Controller → Service → Prisma → PostgreSQL`. Controller описывает HTTP-контракт, получает authentication context и валидирует вход. Service проверяет бизнес-правила и ownership, управляет DB transaction. PrismaService предоставляет Prisma и транзакционный клиент. Универсальный repository поверх Prisma, CQRS, event bus, инфраструктура domain events и дополнительные application layers не вводятся.

| Модуль                        | Ответственность                                           |
| ----------------------------- | --------------------------------------------------------- |
| `AuthModule`                  | Регистрация, вход/выход, JWT cookie, guard, rate limiting |
| `UsersModule`                 | Профиль, настройки валюты/timezone, получение владельца   |
| `CategoriesModule`            | Стандартные категории, CRUD, типы и архивирование         |
| `TransactionsModule`          | Операции, денежные расчеты, поиск/фильтры, экспорт        |
| `BudgetsModule`               | Лимиты и использование бюджета                            |
| `RecurringTransactionsModule` | Правила, календарный расчет и scheduler                   |
| `DashboardModule`             | Агрегации и детерминированные Financial Insights          |
| `ImportsModule`               | CSV parsing, mapping, проверка и импорт                   |
| `AuditModule`                 | Атомарная запись снимков и чтение журнала                 |
| `HealthModule`                | Liveness и readiness                                      |

Модули экспортируют только нужные сервисные операции. Создание транзакции вручную, из CSV и scheduler использует одинаковые проверки и расчеты; внутренний метод принимает транзакционный Prisma-клиент, чтобы вызывающий сервис контролировал атомарность. Audit writer использует тот же клиент и не открывает независимую транзакцию. Общие money/date-функции остаются чистыми и тестируемыми; отдельная доменная платформа не нужна.

## 8. Доменная модель

Модель соответствует `DISCOVERY.md`, разделы 7 и 20. `User` владеет `Category`, `Transaction`, `Budget`, `RecurringTransaction` и `AuditEntry`. Семейный demo-профиль — самостоятельный пользователь, без общего пространства и дополнительных ролей.

`Category` определяет тип операции. `Transaction` хранит исходную сумму/валюту, курс и рассчитанную сумму в основной валюте. `Budget` привязан к expense-категории и календарному месяцу. `RecurringTransaction` — шаблон, из которого создаются независимые редактируемые `Transaction` со ссылкой на правило и дату occurrence. `AuditEntry` хранит исторический снимок, который остается читаемым после удаления основной записи.

Связи: `User 1:N` для каждой принадлежащей ему сущности; `Category 1:N` для операций, бюджетов и правил; `RecurringTransaction 1:N Transaction`. Не добавляются кошельки, счета, переводы, семейное членство и история импорта.

## 9. База данных и инварианты

Основные таблицы и поля берутся из `DISCOVERY.md`, раздел 20; имена таблиц в PostgreSQL — `users`, `categories`, `transactions`, `budgets`, `recurring_transactions`, `audit_entries`. Prisma-модели сохраняют английские identifiers с явным mapping к таблицам.

| Таблица                  | Ключевые данные и ограничения                                                                                                                                           |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`                  | Уникальный нормализованный `email`, `passwordHash`, `displayName`, `baseCurrency`, IANA `timeZone`, `themePreference`, timestamps                                       |
| `categories`             | `userId`, `name`, `type`, `icon`, `color`, `archivedAt`; принадлежность пользователю                                                                                    |
| `transactions`           | Владелец, категория, тип, `amount`, `currency`, `exchangeRate`, `amountInBaseCurrency`, `description`, `transactionDate`, `source`, необязательная пара recurring-полей |
| `budgets`                | Владелец, expense-категория, `year`, `month`, `limitAmount`; `UNIQUE(userId, categoryId, year, month)`                                                                  |
| `recurring_transactions` | Владелец, категория, денежный шаблон, `frequency`, `dayOfMonth`, `startDate`, `endDate`, `nextOccurrenceDate`, `archivedAt`                                             |
| `audit_entries`          | `userId`, `entityType`, `entityId`, `action`, `before`, `after`, `createdAt`; снимки `JSONB`                                                                            |

Деньги и курсы — `NUMERIC/DECIMAL`, бизнес-даты — `DATE`, системные `createdAt`, `updatedAt`, `archivedAt` — `TIMESTAMPTZ`. `transactionDate`, `recurringOccurrenceDate`, `startDate`, `endDate`, `nextOccurrenceDate` не преобразуются через полночь UTC. `year/month` бюджета — целые календарные значения; `month` ограничен диапазоном 1–12.

Технический подход к точности: достаточно емкие decimal-колонки, предварительный ориентир `NUMERIC(24,8)` для сумм и `NUMERIC(24,12)` для курсов. На Stage 2 точность закрепляется вместе с допустимыми диапазонами входа и тестами переполнения. Расчеты выполняются decimal-арифметикой; нормализованная сумма округляется один раз до точности основной валюты по правилу округления половины вверх. Каталог поддержанных валют и их точность хранится локально и проверяется сервером. Это техническая политика расчета, а не внешняя FX-интеграция. API передает денежные значения десятичными строками; число для отрисовки графика не используется для последующих финансовых расчетов.

Обязательные ограничения БД:

- PK и FK с запретом каскадного удаления финансовой истории; `userId` обязателен во всех принадлежащих пользователю таблицах.
- Case-insensitive уникальность email: нормализация на сервере и уникальный индекс на `lower(email)` в SQL-миграции.
- `CHECK(amount > 0)`, положительный `exchangeRate`, положительный `limitAmount`, допустимые enum-значения типов и источников; диапазон `dayOfMonth` 1–31, `frequency = MONTHLY`, `endDate >= startDate`, если конец указан.
- `UNIQUE(userId, categoryId, year, month)` для бюджета.
- `UNIQUE(recurringTransactionId, recurringOccurrenceDate)` для generated transactions. Два recurring-поля либо заполнены вместе, либо оба `NULL`; source `RECURRING` требует заполненной пары.
- Составные FK `(userId, categoryId)` на уникальную пару `(userId, id)` категории, аналогичная связь операции с правилом, исключают межпользовательские ссылки. Обычного FK по `id` для ownership недостаточно.
- У audit корректная форма снимков: `CREATE` — только `after`, `DELETE` — только `before`, `UPDATE/ARCHIVE` — оба. Полиморфный `entityId` не имеет каскадного FK на удаляемую сущность.

Сопоставление типа категории, ее активность, запрет смены основной валюты и расчет суммы затрагивают несколько записей; это проверки сервиса внутри DB transaction, а не недопустимый cross-table `CHECK`. Конкурирующие изменения категории/владельца сериализуются блокировкой соответствующей строки. Если Prisma не выражает нужное ограничение или блокировку, используется небольшая проверяемая SQL-миграция или параметризованный SQL, без универсальной обертки над ORM.

Индексы следуют запросам: `transactions(userId, transactionDate, id)`, `(userId, categoryId, transactionDate)`, `(userId, type, transactionDate)`; индексы FK; `audit_entries(userId, createdAt, id)` и `(userId, entityType, entityId)`; индекс активных правил по `nextOccurrenceDate`. Уникальный ключ бюджета дополняется `(userId, year, month)`, если нужен для месячного списка. Индексы по сумме/валюте и поиску добавляются после анализа запросов, не для каждой колонки заранее.

## 10. REST API и контракты

Префикс — `/api/v1`. Ресурсы: `/auth`, `/transactions`, `/categories`, `/budgets`, `/recurring-transactions`, `/dashboard`, `/imports`, `/audit-log`, `/settings`. Экспорт — операция ресурса транзакций; отдельный сервис не требуется. Имена — существительные, статусы соответствуют HTTP. Swagger UI планируется по `/docs`, проксируется через `web` и позволяет проверить реальный API с cookie-auth.

Единый контракт списков: `items`, `page`, `pageSize`, `total`; пагинация серверная, `page` начинается с 1. Для Transaction Explorer допустимы `pageSize = 10 | 25 | 50`. Фильтры передаются query-параметрами, валидируются и применяются до подсчета `total`. История аудита и остальные растущие списки используют тот же контракт; компактные списки выбора имеют отдельное явное назначение.

Транзакции поддерживают поиск по `description`/названию категории, диапазон дат, тип, категорию, сумму min/max и валюту; разрешенные сортировки: новые/старые сначала, сумма по возрастанию/убыванию. Для сопоставления разных валют фильтр суммы и сортировка используют `amountInBaseCurrency`; UI явно подписывает основную валюту. Это уточнение технического контракта для реализации не изменяет сохраненную исходную сумму. Сортировка всегда дополняется `id` для стабильной пагинации. Даты в API — `YYYY-MM-DD`, timestamps — ISO 8601 с timezone, деньги — decimal strings.

DTO, ответы, cookie security scheme, примеры и ошибки описываются в OpenAPI на русском языке. Спецификация генерируется из backend-контракта, затем из нее генерируются frontend types/client в `packages/api-client`. На Stage 1 выбран Orval 8.33.0 (Fetch client/types и поддержка будущих TanStack Query hooks). Сейчас `packages/api-client` содержит только manifest и описание границы, без exports, DTO и установленного generator. На Stage 2 Orval устанавливается в этой точной версии с lockfile и проверяется цикл на реальном API. Генерируемые файлы не редактируются вручную. CI воспроизводит генерацию и обнаруживает рассинхронизацию. Prisma-модели не являются публичными API DTO. Ошибки всех ресурсов используют раздел 19.

## 11. Аутентификация, авторизация и сессия

Пароль хешируется Argon2id. Регистрация атомарно создает пользователя и стандартные категории с аудитом категорий. Email нормализуется до проверки уникальности; конкурентные регистрации защищает индекс БД. Пользователь выбирает `baseCurrency` и IANA `timeZone`.

`POST /api/v1/auth/register`, `/login`, `/logout` и `GET /api/v1/auth/me` соответствуют Discovery. JWT хранится только в HttpOnly cookie: `SameSite=Strict`, `Path=/`, без расширяющего `Domain`, `Secure` при production HTTPS. В локальном HTTP Compose demo-профиле `Secure` выключен явно, независимо от оптимизированной production-сборки frontend. Нельзя автоматически определять безопасность cookie по произвольному клиентскому заголовку.

Модель сессии v1: подписанный JWT с `sub`, `iat`, `exp`, проверкой алгоритма, issuer и audience; предварительный технический TTL — 24 часа, фиксируется конфигурацией и тестами на Stage 4. Refresh tokens и таблица сессий не требуются. По истечении срока нужен повторный вход. Logout удаляет cookie с теми же path/атрибутами; сервер не хранит список отозванных JWT, поэтому ранее скопированный токен действителен до `exp`. Это ограничение сессии без серверного состояния следует учитывать в тестах и документации, не обещая принудительное завершение всех устройств.

Guard проверяет JWT и существование пользователя, формирует authentication context. `userId` для всех запросов, включая CSV, dashboard и audit, берется только из него. Вложенные `categoryId`/`recurringTransactionId` проверяются на принадлежность тому же пользователю. Обращение к чужому ресурсу по ID дает безопасный `404`, коллекции всегда ограничены владельцем. Frontend не является security boundary.

Login/register ограничиваются по частоте; значения лимитов документируются и проверяются на Stage 4. Для одного backend достаточно локального limiter без Redis. Доверие к proxy задается только для известной топологии Nginx, чтобы нельзя было обойти лимит подменой IP-заголовков. Ошибки входа не раскрывают существование аккаунта.

## 12. Безопасность

Минимальная модель угроз: доступ к чужим данным, подделка browser-запросов с cookie, подбор паролей, XSS/SQL injection, утечки в логах, вредоносное содержимое CSV и исчерпание ресурсов загрузкой. Базовые меры закреплены в `DISCOVERY.md`, раздел 23.

Для изменяющих browser-запросов проверяется `Origin` по точному разрешенному origin, включая login/register/logout. Отсутствующий или недоверенный `Origin` не получает автоматического исключения; тестовые и документированные клиенты передают корректный origin. GET не изменяет данные. `SameSite=Strict` дополняет эту проверку. Same-origin Compose не требует открытого CORS; при явно настроенной разработческой схеме допустим только точный allowlist, без `*` с credentials.

Обязательны серверная validation, запрет mass assignment служебных полей, параметризованный SQL, безопасное текстовое отображение описаний и audit, ограничения запросов и CSV. `password`, `passwordHash`, JWT, Cookie/Set-Cookie, исходные CSV и финансовые описания не логируются. Пользователь не получает stack trace; production secrets не хранятся в Git и не попадают в frontend bundle.

CSV разбирается как данные без выполнения формул. Проверяются расширение, UTF-8, размер, число строк, структура и значения; одному MIME/имени доверять нельзя. Экспорт экранирует CSV по правилам формата и нейтрализует текстовые ячейки с формульными префиксами (`=`, `+`, `-`, `@`, управляющие символы), чтобы открытие в табличном редакторе не исполняло содержимое. Детали pipeline — раздел 15.

## 13. Транзакции, категории и бюджеты

Сервис транзакций в одной DB transaction проверяет владельца, тип/доступность категории, денежные поля; вычисляет `amountInBaseCurrency`; сохраняет сущность и audit. `amount > 0`, знак не кодирует `INCOME/EXPENSE`. Для основной валюты курс равен 1. Изменение суммы использует прежний snapshot курса; изменение валюты требует нового курса. На клиентское значение normalized amount сервер не полагается.

Появление financial data блокирует смену `baseCurrency`: сервис настроек проверяет операции, бюджеты и recurring rules, включая свидетельство уже удаленных данных в неизменяемом audit. Проверка и создание финансовых данных используют общую блокировку строки пользователя, исключая гонку первого ввода со сменой валюты. Timezone остается настройкой календарного поведения scheduler, а не способом сдвинуть существующие business dates.

Удаление категории проверяет ссылки операций, бюджетов и правил. Неиспользованная категория удаляется, используемая архивируется. FK с `RESTRICT` защищает от гонок удаления. Исторические запросы не отфильтровывают архивные категории. Сервер запрещает новые операции, бюджеты и правила с архивной категорией. Редактирование исторической операции может сохранить ее прежнюю архивную категорию; выбрать другую архивную категорию нельзя. Изменение типа используемой категории, нарушающее существующие связи, отклоняется с `CONFLICT`.

При архивировании категории связанные активные recurring rules деактивируются в той же транзакции с отдельными audit entries: scheduler не создает новые операции с архивной категорией. Интерфейс подтверждения объясняет это последствие. Так согласуются правила запрета новых операций и сохранения истории без введения новых состояний.

Бюджет — лимит в основной валюте, только для expense-категории. Уникальность месяца обеспечивает БД, конкурентный дубль превращается в `409`. Использование — сумма `amountInBaseCurrency` expense-операций категории в календарном месяце по `transactionDate`. Изменение/удаление операции отражается в агрегации, отдельный изменяемый счетчик не хранится. Прогресс показывает реальное превышение текстом, даже если полоса визуально ограничена 100%. Копирование прошлого месяца остается необязательным действием, автоматического переноса нет.

## 14. Планировщик регулярных операций

Nest scheduler выполняется внутри `api`, без очереди и отдельного worker. При запуске и затем периодически он выбирает активные правила, определяет календарный `today` по IANA `timeZone` владельца и обрабатывает все даты `nextOccurrenceDate <= today` в пределах start/end. Timezone контейнера не определяет наступление платежа.

Чистая календарная функция рассчитывает очередной месяц от исходного `dayOfMonth`, а не прибавлением 30 дней и не от уже укороченной даты: правило на 31-е дает последний день февраля и снова 31-е марта. Тестируются 28/29/30/31, високосный год и границы timezone. `endDate` включительна; после последней допустимой даты правило больше не исполняется. Новая дата всегда строго позже обработанной.

Каждый occurrence обрабатывается короткой DB transaction: блокировка пользователя/правила в согласованном порядке → повторная проверка активности и даты → создание `Transaction` с `source=RECURRING` и исходной `recurringOccurrenceDate` → audit `CREATE` → продвижение `nextOccurrenceDate` с audit `UPDATE` правила. Все изменения фиксируются вместе. Уникальность пары recurring-полей — окончательная защита от параллельного создания, а блокировка предотвращает гонку с редактированием правила. Ошибка откатывает и запись, и указатель; следующий проход повторит попытку. Catch-up идет ограниченными пачками без пропуска оставшегося долга.

Редактирование правила не должно менять параметры еще не восстановленных прошлых occurrence. Перед сохранением измененного шаблона сервис завершает его catch-up по прежним параметрам до текущей даты; затем под той же схемой блокировок проверяет отсутствие долга и задает новую будущую дату. При большом долге обработка продолжается обычными пачками, а изменение не объявляется сохраненным до завершения проверки. Пересчет не сбрасывает указатель в начало уже обработанной истории. Этот случай проверяется отдельно от редактирования уже созданных транзакций.

Редактирование шаблона не переписывает generated transactions; после появления они редактируются независимо, сохраняя recurring-пару даже при изменении `transactionDate`. Чтобы удаленная пользователем generated transaction не появилась заново при пересчете расписания, проверка учитывает также ее исторический audit `CREATE` с recurring-парой. Проверка выполняется под блокировкой правила. Отдельная таблица occurrence не нужна; имеющийся неизменяемый audit сохраняет факт генерации. Правило, когда-либо создававшее операции, не удаляется физически даже после удаления этих операций — это проверяется по истории. Hard delete допустим только до первой генерации.

Сбой одной записи логируется с идентификатором и не скрывается; проход продолжает независимые правила. Ошибки данных не приводят к бесконечному плотному циклу. Перезапуск восстанавливает работу с сохраненного `nextOccurrenceDate`; scheduler не зависит от памяти процесса. Изменение timezone не переписывает историю и не отменяет защиту от повторов.

## 15. CSV: импорт и экспорт

Pipeline: `upload → parse → preview → mapping → validation → duplicate analysis → import → result`. Ограничения: `.csv`, UTF-8, не более 5 MB и 10 000 строк данных. Лимит тела учитывает небольшой multipart overhead, но лимит самого файла остается 5 MB. Парсер корректно обрабатывает кавычки, разделители, переносы внутри поля и BOM; не угадывает неоднозначные даты/числа молча.

Мастер хранит исходный файл и mapping в состоянии текущей страницы. Backend получает файл для preview/validation и повторно для подтвержденного импорта; постоянное файловое хранилище, import history subsystem и фоновая инфраструктура не нужны. Пользователь может вернуться к mapping до записи в БД. После ухода со страницы незавершенный импорт не считается сохраненным.

1. Сервер проверяет ограничения и разбирает файл; возвращает колонки, небольшой preview и ошибки структуры.
2. Пользователь сопоставляет колонки и каждое неизвестное значение категории с существующей своей категорией; категории автоматически не создаются.
3. Сервер проверяет строки, тип категории, активность, decimal-суммы, дату и валюту. При отсутствии достаточного foreign-currency курса пользователь задает его для соответствующей валюты до импорта. Придуманный или внешний курс не применяется.
4. Потенциальные дубли ищутся внутри файла и среди собственных операций по fingerprint из `DISCOVERY.md`, раздел 7: владелец, дата, сумма, валюта, тип, нормализованное описание. Это эвристика без уникального индекса: реальные одинаковые операции допустимы.
5. Пользователь видит ошибки и дубли; по умолчанию дубли пропускаются, явное включение разрешает их импорт. Подтверждение содержит mapping и решения по строкам, но не доверенные суммы/ownership.
6. На import сервер повторяет validation и duplicate analysis по актуальной БД. Новые потенциальные дубли не импортируются без явного согласия; результат сообщает пропуски. Валидные выбранные строки сохраняются с `source=CSV` и audit, невалидные пропускаются. Номера строк и причины сохраняются в ответе для экрана результата.

Для допустимого размера достаточно синхронного HTTP-запроса с ограниченным потреблением памяти и пакетной записью внутри одной DB transaction для выбранного валидного набора. Пользовательские ошибки отсекаются до записи; неожиданная DB-ошибка откатывает весь этот набор и возвращает безопасную ошибку. Так partial import означает осознанный пропуск невалидных строк, а не скрытое частичное завершение после сбоя. Timeout и размер пачек проверяются на 10 000 строках; аудит записывается пакетно в той же транзакции.

Кнопка подтверждения блокируется на время отправки. Автоматический повтор изменяющего запроса после сетевого сбоя не выполняется: пользователь возвращается к проверке дублей, поскольку ответ мог потеряться после commit. Гарантия exactly-once для произвольно повторенного CSV не заявляется и не подменяет разрешенные одинаковые операции.

Экспорт использует тот же серверный построитель фильтров/сортировки и ownership, что список, но без ограничения текущей страницы. Все подходящие записи выдаются потоком/пачками с устойчивым порядком; форматирование и CSV-экранирование централизованы. Проверяются объем, Unicode, формульные префиксы и отсутствие чужих данных.

## 16. Аудит

`AuditModule` предоставляет writer для `Transaction`, `Budget`, `Category`, `RecurringTransaction` и API только для чтения. Domain mutation и audit entry находятся в одной DB transaction с одним Prisma-клиентом. Ошибка audit отменяет изменение сущности. Аудит нужен с первых доменных мутаций; Stage 10 добавляет полноценное чтение и UI, а не начинает запись задним числом.

Снимки `before/after` соответствуют семантике `CREATE/UPDATE/DELETE/ARCHIVE` из `DISCOVERY.md`, раздел 7. Это разрешенный набор доменных полей, без паролей и токенов. Decimal сохраняется строкой, бизнес-дата — строкой даты; человекочитаемые названия категории включаются в снимок, чтобы последующее переименование/удаление не разрушило diff. Для scheduler владельцем записи является владелец правила, системное происхождение видно из `source` операции.

Пользователь не имеет update/delete API для audit; runtime-доступ к таблице ограничивается чтением/вставкой, учетная запись миграций отделяется от runtime. Полиморфная ссылка сохраняется после удаления сущности, снимки не пересчитываются из текущего состояния. Чтение, фильтры и пагинация всегда ограничены `userId` из auth context.

Frontend `AuditDiff` преобразует известные поля в русские подписи и форматированные before/after, показывает только изменения. Raw JSON не заменяет пользовательский diff. При добавлении полей обновляются сериализатор, OpenAPI и форматирование; неизвестные исторические поля отображаются безопасно, без падения экрана.

## 17. Dashboard и аналитика

`DashboardModule` агрегирует на сервере данные пользователя за выбранный календарный месяц: доходы, расходы, net, savings rate, распределение расходов, top-5, бюджеты, ближайшие recurring operations и Financial Insights. Денежные агрегаты используют сохраненный `amountInBaseCurrency`, а не текущие курсы. Архивные категории участвуют в исторических расчетах.

Dashboard API принимает месяц и год, возвращает готовую согласованную модель экрана. SQL/Prisma выполняет группировки и суммы в PostgreSQL, не выгружая всю историю в Node.js или браузер. Связанные агрегаты читаются в согласованном снимке БД. Six-month trend включает выбранный месяц и предыдущие пять, пустые месяцы заполняются нулями. Business dates фильтруются полуоткрытым диапазоном от начала месяца до начала следующего.

При `income > 0` savings rate равен `(income - expenses) / income × 100`, при отсутствии дохода API возвращает `null` и UI объясняет отсутствие определенного процента. Net — результат периода, не баланс банковского счета.

Financial Insights — чистые детерминированные правила поверх агрегатов: рост расходов, изменение savings rate, превышение бюджета, крупнейшая категория, существенные изменения месяц к месяцу. Правила имеют зафиксированные пороги, минимальные условия достаточности данных и стабильный приоритет, проверяются на fixtures; показываются 2–4 наиболее релевантных при наличии оснований, без выдуманных выводов для пустой истории. При нулевой базе сравнения нет фиктивного процента. Пороговые значения фиксируются вместе с реализацией Stage 7. LLM и внешний финансовый советник отсутствуют.

## 18. Три уровня валидации

| Уровень  | Ответственность                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| Frontend | Формат ввода, обязательные поля, быстрые подсказки и отображение ошибок сервера; не граница безопасности            |
| Backend  | Авторитетная проверка схемы, диапазонов, бизнес-правил, ownership, валюты/даты, согласованности связанных сущностей |
| Database | PK/FK, уникальность, `CHECK`, транзакции и защита от конкурентных нарушений                                         |

Генерируемые TypeScript types обеспечивают статическую совместимость, но не runtime validation. Backend отклоняет неожиданные поля и не преобразует неоднозначные значения молча. В каждой доменной функции явно определено, какие проверки выполняются до записи и какие повторяются внутри транзакции.

## 19. Ошибки

Все модули используют один Problem Details-подобный контракт из Discovery:

```json
{
  "type": "validation_error",
  "title": "Ошибка валидации",
  "status": 400,
  "detail": "Переданы некорректные данные",
  "errors": {},
  "traceId": "..."
}
```

`errors` — словарь путей полей к спискам русских сообщений, пустой при отсутствии полевых ошибок. Общий exception filter переводит validation, auth, domain и Prisma-ошибки в этот контракт; ограничитель частоты тоже не возвращает собственный формат. Категории `VALIDATION`, `AUTHENTICATION`, `AUTHORIZATION`, `NOT_FOUND`, `CONFLICT`, `RATE_LIMIT`, `INTERNAL` получают документированные стабильные значения `type` и статусы 400/401/403/404/409/429/500.

Неожиданная ошибка логируется со stack trace и `traceId` после redaction; пользователю возвращается безопасное описание. Ожидаемый конфликт не маскируется под 500. Frontend показывает ошибки полей или общую ошибку с возможностью повтора там, где это безопасно; silent failures и пустой catch запрещены.

## 20. Логи и проверка здоровья

Backend пишет структурированные JSON-логи: безопасный request/trace ID, HTTP method, шаблон route, status, duration. ID создается сервером либо принимается после ограничения длины/формата. Он возвращается клиенту и связывает ошибку с серверным логом. Полные query/body/headers по умолчанию не логируются.

Ошибки содержат безопасный контекст и stack только на сервере. Redaction применяется к auth-данным, финансовым описаниям, снимкам audit и CSV; обработчик ошибки не сериализует весь request. Scheduler пишет длительность прохода, число созданий/пропусков и ошибки, startup — стадии готовности без секретов.

`/health/live` подтверждает работу процесса; `/health/ready` дополнительно проверяет PostgreSQL и завершенный startup. Пока миграции/seed не завершены, готовность не объявляется. Достаточно stdout/stderr контейнеров и healthchecks; Grafana, Prometheus, ELK и распределенный tracing не добавляются.

## 21. Стратегия тестирования

Минимум задания — 10 unit/integration тестов — обязателен и превышается. Цель Discovery: 25–40 содержательных автоматических тестов плюс Playwright smoke suite. Число не заменяет покрытие рисков и не является запретом на дополнительные необходимые проверки. Тесты добавляются вместе с этапами, Stage 11 закрывает пробелы.

| Уровень             | Приоритетные проверки                                                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit backend        | Decimal-расчеты и округление, календарь 28/29/30/31, timezone, fingerprint CSV, savings rate без дохода, правила Insights                                           |
| Integration backend | Реальная тестовая PostgreSQL: auth/изоляция, тип/архив категории, уникальность бюджета, конкурентная recurring-генерация и catch-up, rollback audit, migration/seed |
| Компоненты frontend | Vitest + Testing Library: формы, ошибки validation, фильтры, loading/empty/error, mapping, keyboard/focus                                                           |
| E2E                 | Playwright: login → dashboard; создание операции; фильтрация; CSV import; проверка изоляции двух пользователей                                                      |

На Stage 1 backend-тесты компилируются тем же TypeScript с Nest decorator metadata и запускаются стабильным `node:test`; это проверено на реальном HTTP bootstrap, без Jest/SWC-трансформеров. Выбор поддерживает ESM NestJS 12 и не требует дополнительных test dependencies. В дальнейшем замена PostgreSQL на SQLite/in-memory не допускается для integration. Тестовая БД изолирована от demo-volume, состояние воспроизводимо. Время scheduler передается через тестируемый источник времени, а не реальные ожидания. Отдельно проверяются конкуренция и перезапуск, границы денежных диапазонов, отсутствие audit при rollback, CSV с 10 000 строками и экспорт за пределами страницы.

Дополнительные E2E для budget/recurring/audit допустимы при наличии времени, но соответствующие бизнес-правила обязательно проверяются unit/integration. Доступность и mobile проверяются вместе с UI; финально выполняются smoke и ручная демонстрация. Точный набор команд документируется после появления конфигурации, результаты — только после запуска.

## 22. Seed

Seed детерминированный и идемпотентный: стабильные identifiers, фиксированные шаблоны и управляемая опорная дата, повторный запуск не дублирует записи и не перетирает пользовательские изменения. Временная опора выбирается при первом заполнении и затем восстанавливается из стабильной seed-записи; так история остается актуальной при первой демонстрации и не сдвигается при restart. В тестах опорная дата задается явно.

Обязательный минимум задания: 200+ транзакций за 6 месяцев, 12 категорий, 3 бюджета, 2 пользователя. План Discovery: 260–320 транзакций, 14–16 категорий, не менее шести содержательных месяцев, не менее трех бюджетов с дополнительными сценариями. Числа относятся к demo-набору; данные распределены между двумя независимыми аккаунтами, у каждого есть собственные категории и история. Новому пользователю стандартные категории создаются отдельно при регистрации.

Набор включает 2–3 валюты с сохраненными курсами, доходы/расходы, top-5, высокий/низкий savings rate, бюджет около лимита и превышенный, изменения месяц к месяцу, recurring salary/subscriptions и понятные audit diffs. Подписи и описания русские. Все fixtures соблюдают те же ограничения, что реальные операции; audit seed отражает последовательность содержательных изменений.

Повторный seed не воскрешает удаленные demo-операции: используется атомарная инициализация набора с устойчивым признаком завершения в истории seed-данных, а не безусловный upsert каждой удаленной строки. Детали идентификации фиксируются на Stage 2, без отдельной продуктовой подсистемы. Частично неуспешная первичная загрузка откатывается; параллельный startup защищается DB lock. В Stage 2 закладывается механизм и начальный набор; доменные сценарии дополняются на своих этапах, окончательный объем проверяется до сдачи.

Два demo-профиля: личный и семейный. Реальные credentials появятся при реализации seed, затем будут опубликованы на Login screen и в README. Stage 0 не придумывает их.

## 23. Docker и развертывание

Целевой приемочный сценарий после реализации:

```bash
git clone <repo>
cd <repo>
docker compose up
```

Это будущий контракт Docker; текущие команды локального Foundation описаны в README. Единственные внешние предпосылки — Git, работающий Docker с Compose и доступ для загрузки образов/зависимостей. Не нужны локальные Node.js/pnpm, ручное создание БД, `.env`, миграции, seed или редактирование конфигурации.

`postgres`: закрепленный образ, persistent volume, healthcheck. `api`: многостадийная сборка с lockfile, сгенерированным Prisma client, миграциями и исполняемым seed внутри образа. `web`: production build Vite, раздаваемый Nginx, fallback для React Router и отдельное проксирование `/api/v1` и `/docs` перед fallback.

Порядок startup:

1. Compose запускает PostgreSQL и ожидает успешного healthcheck.
2. Entrypoint `api` дополнительно ожидает реальной доступности БД с ограниченными повторами.
3. Отдельным миграционным доступом применяются сохраненные миграции; runtime-роль получает только нужные права, включая insert/select для audit.
4. Идемпотентный seed выполняется автоматически; секреты локального demo-профиля и необходимые параметры имеют готовые безопасно обозначенные demo defaults.
5. При успехе запускается NestJS с runtime-доступом, затем scheduler. При ошибке миграций/seed startup завершается ненулевым кодом; API не объявляется готовым с неполной БД.
6. `/health/ready` подтверждает PostgreSQL; `web` зависит от готового `api` и имеет собственный healthcheck раздачи UI. Readiness backend проверяется отдельно от наличия статического HTML.

Состояние PostgreSQL сохраняется при обычном restart. Повторный запуск не требует ручного исправления схемы и не дублирует demo-данные. Удаление volume — только явная процедура сброса, не обычная команда запуска. У API нет постоянного volume для CSV и нет зависимости от host-installed packages.

Compose по умолчанию — локальная учебная демонстрация с HTTP и явно обозначенными demo secrets. Production HTTPS требует внешней конфигурации секретов и `Secure` cookie; это отдельный режим и не обязательная ручная настройка для локальной сдачи. Не следует публиковать локальные demo defaults как production-конфигурацию. Порты, имена переменных и фактические адреса фиксируются после проверки Stage 2.

Обязательные проверки: первый запуск из чистой копии без `.env` и volume; повторный запуск с существующим volume; миграции/seed без дублей; отказ БД и корректная readiness; deep link UI; Swagger за Nginx; cookie-auth через тот же origin. На Stage 2 проверяется инфраструктура, на Stage 12 — весь продукт тем же сценарием. Это главный ранний технический риск.

## 24. CI и история разработки

GitHub Actions постепенно реализует обязательный pipeline: установка из lockfile → lint → проверка форматирования → typecheck → tests → build → проверка Docker build. Сборка Docker обязательна для принятого scope Discovery, хотя в общих требованиях задания отдельно названа опциональной. Unit/integration используют настоящую PostgreSQL service с миграциями; frontend build проверяет генерируемый API-клиент.

Foundation дает начальные install/lint/format/typecheck/tests/build; Stage 2 добавляет PostgreSQL, генерацию контрактов и Docker build; следующие этапы расширяют реальные тесты. Playwright может выполняться отдельным job с поднятым Compose и ожиданием readiness, если это упрощает время выполнения и диагностику; сам smoke suite обязателен к финалу. Отчеты падений и E2E artifacts не должны содержать секреты.

Адекватная Git history обязательна: архитектурная документация должна попасть в commit до application code, затем каждый законченный шаг оформляется логически. Preflight Stage 1 подтвердил существующий Git-репозиторий и отдельный commit документации `bb3ff1a` до первого application code. Remote `origin` связан с GitHub. Агент не выполняет commit самовольно. Финальная сдача включает GitHub-репозиторий и успешный CI.

## 25. Производительность

Цель — десятки тысяч транзакций пользователя с отзывчивым UI. Базовые меры: индексы по фактическим фильтрам, серверные pagination/filtering/sorting, агрегации PostgreSQL, отсутствие N+1, debounce поиска, TanStack Query caching, лимиты файлов и ограниченный preview CSV. Dashboard получает готовые агрегаты одним контрактом, экспорт читает данные пачками.

Медленные запросы проверяются на реалистичном объеме через планы выполнения и длительности. Offset-pagination достаточно для текущего масштаба; усложнение оправдано только измеренным ограничением. Redis cache, materialized views и отдельное поисковое хранилище заранее не вводятся.

## 26. Решения и компромиссы

| Решение                              | Причина и компромисс                                                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| Модульный монолит NestJS             | Явные предметные границы и общие DB transactions при одном процессе; независимое масштабирование модулей пока не требуется |
| Отдельный REST backend               | Выполнение задания, живой Swagger, самостоятельная серверная авторизация; контракт синхронизируется генерацией             |
| PostgreSQL                           | Decimal, даты, FK/unique/check, JSONB и агрегации; нужна настоящая БД в integration и Compose                              |
| Prisma                               | Типизированный доступ и управляемые миграции; сложные constraints/блокировки остаются в небольшом явном SQL                |
| TypeScript во всем приложении        | Совместимость типов и сопровождение; типы не заменяют runtime validation                                                   |
| Курс-снимок без внешнего FX API      | Историческая воспроизводимость и автономный demo-запуск; foreign-currency курс вводится пользователем                      |
| Scheduler внутри backend             | Достаточно для monthly/catch-up; конкурентность и перезапуск защищаются БД                                                 |
| Без Redis/RabbitMQ/микросервисов     | Для текущего объема достаточно PostgreSQL и одного API; меньше инфраструктурных отказов                                    |
| Детерминированные Financial Insights | Объяснимость и воспроизводимые тесты, нет LLM и зависимости от внешнего сервиса                                            |
| Same-origin через Nginx              | Единое cookie-поведение; proxy и локальный HTTP требуют ранних E2E проверок                                                |

Все сознательно исключенные возможности остаются исключенными согласно `DISCOVERY.md`, раздел 34. Необязательные улучшения из раздела 32 не вытесняют обязательные функции и светлую тему.
