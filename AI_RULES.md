# Finora — правила работы coding-agent

## Перед изменениями

Полностью прочитай [PROJECT.md](PROJECT.md), [DISCOVERY.md](DISCOVERY.md), [ARCHITECTURE.md](ARCHITECTURE.md) и релевантный этап [ROADMAP.md](ROADMAP.md). Затем изучи существующий код, найди подходящие API, types, components, utilities и tests до создания новых.

Приоритет источников: `PROJECT.md` → `DISCOVERY.md` → `ARCHITECTURE.md` → `ROADMAP.md`; код отражает фактическую реализацию. Обязательные требования задания нельзя ослаблять. Discovery повторно не проводи, утвержденные продуктовые решения молча не меняй.

## Во время реализации

- Работай только над текущим Stage/task; выполняй небольшие законченные изменения, избегай массовой генерации всего приложения за один проход. На Stage 0 разрешены только пять документов, перечисленных в roadmap; Stage 1 самостоятельно не начинай.
- Сохраняй strict TypeScript. Не используй необоснованные `any`, `@ts-ignore` или отключения lint.
- Не оставляй обязательную работу как TODO, не подменяй реальную реализацию mock/stub. Тестовые doubles допустимы только внутри подходящих тестов, не вместо PostgreSQL integration.
- Не скрывай exceptions, не оставляй пустые catch и silent failures. Используй единый API error contract.
- Переиспользуй существующие компоненты и утилиты; соблюдай разделение ответственности. Не меняй работающие функции без причины и не добавляй слои/зависимости «на всякий случай».
- Учитывай edge cases, loading/error/empty/filtered-empty/success, подтверждение разрушительных действий, responsive UI, клавиатуру и focus.
- Проверяй authorization и ownership на сервере, включая связанные IDs. Клиентский `userId` не определяет владельца. Не логируй секреты и финансовые данные.
- Записывай audit атомарно с каждой применимой доменной мутацией с момента ее появления; интерфейс Stage 10 не оправдывает отложенную запись истории.
- Все human-readable документы, UI, ошибки и OpenAPI descriptions пиши на русском. Технические identifiers сохраняй на английском без транслитерации.

## При противоречиях

Если requirement, `PROJECT.md`, `DISCOVERY.md`, `ARCHITECTURE.md`, roadmap или код расходятся, не выбирай решение молча. Приостанови затронутую часть и явно опиши: **1) противоречие; 2) влияние; 3) рекомендуемое безопасное решение**. Исходные документы самостоятельно не переписывай. Если противоречия нет, не задавай дополнительных вопросов по уже утвержденным решениям.

## После изменений

Запусти релевантные lint, проверку форматирования, typecheck, tests, build, E2E и Docker checks согласно этапу. Не утверждай, что проверка прошла, если она не запускалась успешно. Указывай незапущенные/заблокированные проверки и причину. Для Stage 0 проверяются только документы и состав файлов; команды приложения еще отсутствуют.

После значимого этапа актуализируй [REPORT.md](REPORT.md): реальные AI-инструменты, выполненные действия, решения, проблемы и результаты проверок. По необходимости обнови архитектуру, README и roadmap; не фабрикуй историю. Проверь итоговые `git status`/`git diff`, если Git доступен, и предложи логический commit. Самостоятельно не выполняй commit без явного разрешения. Документация Stage 0 должна быть зафиксирована в Git до первого application code.
