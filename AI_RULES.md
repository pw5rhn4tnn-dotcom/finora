# Finora — правила работы coding-agent

## Перед изменениями

Полностью прочитай [PROJECT.md](PROJECT.md), [DISCOVERY.md](DISCOVERY.md), [ARCHITECTURE.md](ARCHITECTURE.md) и релевантный этап [ROADMAP.md](ROADMAP.md). Затем изучи существующий код, API, types, components, utilities и tests до создания новых сущностей.

Приоритет источников: `PROJECT.md` → `DISCOVERY.md` → `ARCHITECTURE.md` → `ROADMAP.md`; код отражает фактическую реализацию. Обязательные требования нельзя ослаблять. Discovery повторно не проводи, утверждённые решения молча не меняй.

## Во время реализации

- Работай только над текущим Stage/task. Не начинай следующий Stage без явного разрешения.
- Сохраняй strict TypeScript. Не используй необоснованные `any`, `@ts-ignore`, отключения lint и обходы type safety.
- Не оставляй обязательную работу как TODO и не подменяй production-логику mock/stub. Test doubles допустимы только в тестах.
- Не скрывай exceptions и silent failures. Используй единый API error contract.
- Переиспользуй существующие компоненты и утилиты. Не меняй работающий код и не добавляй зависимости/слои без необходимости.
- Учитывай edge cases, loading/error/empty/success, destructive confirmations, responsive UI, клавиатуру, focus и accessibility.
- Authorization и ownership проверяй на сервере, включая связанные IDs. Клиентский `userId` не определяет владельца.
- Не логируй секреты и финансовые данные.
- Audit записывай атомарно с применимой доменной мутацией с момента появления audit-механизма.
- Human-readable документацию, UI, ошибки и OpenAPI descriptions пиши на русском. Technical identifiers оставляй на английском.

## При противоречиях

Если requirement, `PROJECT.md`, `DISCOVERY.md`, `ARCHITECTURE.md`, `ROADMAP.md` или код расходятся, не выбирай решение молча. Останови затронутую часть и явно опиши: **1) противоречие; 2) влияние; 3) рекомендуемое безопасное решение**.

Если противоречия нет, не задавай повторных вопросов по уже утверждённым решениям.

## После изменений

Запусти релевантные lint, format check, typecheck, tests, build, E2E и Docker checks согласно Stage. Не утверждай, что проверка прошла, если она не запускалась успешно. Незавершённые или заблокированные проверки указывай явно с причиной.

Актуализируй [REPORT.md](REPORT.md), а при необходимости — `ARCHITECTURE.md`, `README.md` и `ROADMAP.md`. Не фабрикуй историю и не скрывай ранние падения или исправления.

Проверь `git status` и `git diff`, если Git доступен. Предлагай логический commit, но не выполняй commit/push без явного разрешения.

## Правила REPORT.md

- Для каждого Stage существует ровно один основной раздел:
  `## DD.MM.YYYY — Stage N: <краткое название>`.
- Дата основного Stage-раздела не меняется из-за последующих исправлений, CI-проверок или повторной приёмки.
- Все последующие события того же Stage добавляются внутрь существующего раздела как `###` подразделы.
- Запрещено создавать второй основной заголовок для уже существующего Stage.
- Название Stage должно соответствовать фактическому scope из `ROADMAP.md`.
- При обновлении отчёта нельзя менять факты, результаты тестов, SHA, root cause или историю ради красивой структуры.
- После изменения `REPORT.md` выполни:
  `pnpm exec prettier REPORT.md --write`,
  `pnpm format:check`,
  `git diff --check`.

Если для Stage уже существует основной раздел, создание второго основного Stage-раздела считается ошибкой.
